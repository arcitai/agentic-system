# Operating through T3 Code

Revision: 0.1.29 · Updated: 2026-10-30

This is a product-specific reference. The portable method can use another native agent tool. Follow the selected version's current documentation; the detailed Nightly examples below retain their original observation dates and are not universal stable commands.

## Linked execution environments

The Lab runs official Stable **0.1.5**: its AgentOps lead since the 29 October 2026 maintenance and its fresh task workers since R7. Linked delegation from the Stable lead to fresh Stable workers was observed on 30 October 2026 (rc1); this is not proof of complete local acceptance. Earlier, the Lab selected Nightly **0.1.4-nightly.20261027.3796** because stable **0.1.3** lacked native remote delegation. Enable **Linked environments** in Settings → Labs on both ends. Foundation prepares the environments; AgentOps starts tasks in them. The link does not create a VM.

In the current Lab, the project-scoped lead creates and removes fresh per-task worker VMs through the native project controller; this was observed in the bounded R7 trial on 29 October 2026 and in the rc1 Stable/Auto delivery on 30 October 2026. The three prepared baseline worker environments, still on 3796, were retired on 30 October 2026 (stopped; disks and verified history copies retained) and are no longer fallbacks; their exit 125 does not qualify a clean stop. The owner's target is one isolated, on-demand sandbox per agent, managed by AgentOps inside its own environment with minimal physical-host actions and no extra coordinator LLM. Those bounded trials do not qualify unattended intake, provisioning without the lead, approval-free operation, account-wide isolation, boot/login startup, updates or GUI restore. Shared worker environments are a weaker optional arrangement. Keep only AgentOps pinned. An app connection and an agent-to-agent link are separate grants; neither gives a worker the lead's source-service connections.

On this release, a Full-access peer link requires `orchestration:read`, `orchestration:operate`, `settings:write` and `source-control:write`. Grant only the selected worker environment. Access administration, provider management and environment maintenance are not required. The caller's own runtime mode and the link's mode both limit the remote work; Full access still permits the worker to use everything available inside its VM. Verify the actual grant and result instead of treating a role name as enforcement.

Use a supported private route and verify the expected environment identity. T3 recognizes actual Tailscale MagicDNS names and Tailscale IPv6 addresses; a `100.64.0.0/10` address alone is not proof of Tailscale. Keep credentials private and retain native authentication and transport checks. The selected host's DNS, proxy and port publication must work together; a successful host request does not prove the same route from a sandbox.

Discover the live tool contract before delegation. `delegate_task` can select `target.environmentId` and `target.projectId`; inspect the returned child, workspace, model and modes. Native following across restarts and revocation handling are upstream capabilities to qualify locally. Record real dispatch, completion/wake, cancellation, refusal and duplicate behavior before enabling unattended intake. See the pinned [remote-access reference](https://github.com/pingdotgg/t3code/blob/b88da91397c247b98c892831d7e759f72ea4db43/docs/user/remote-access.md#link-another-environment) and the installation's qualification record.

On 3796, linked `delegate_task` refused `isolation:worktree`; a second launch without it ran in the remote project's checkout. This does not qualify concurrent writers. A remote dangerous-cleanup permission request did not wake the parent, and `task_status` reported no pending approval. Operator detection and a no-delete steering message recovered that reviewer; an orphaned approval record remained after completion and was left unanswered. Do not late-approve a completed run, install an approval pump or treat these earlier same-environment examples as linked-worktree proof. On 0.1.5, rc1's implementer used a pre-created Git worktree; the linked `isolation:worktree` argument was not retested.

On 30 October 2026, rc1 ran a Stable 0.1.5 lead and its workers in native Auto. Two fresh, sequential reviewers accepted identical bytes after one repair. One reviewer attempt failed with a model transport error; after the same job was inspected, a fresh-context retry completed. No ordinary runtime approval requests were observed. Native unlink of the task links from the Auto lead returned `capability_denied`; the revoked, inert records are held for full-access maintenance. This is one bounded observation ([#32](https://github.com/arcitai/agentic-systems/issues/32#issuecomment-6512720017)), not unattended or approval-free proof.

Later on 30 October 2026, a finite queue ran on 0.1.5. One native `fixed_time` schedule bound to the pinned lead dispatched one queued message; its "succeeded" status means dispatched, not completed. This release has no one-shot or expiry field: the lead disabled the schedule on wake and deleted it at completion, which is observed model behaviour, not enforced expiry. On one candidate, a reviewer's two attempts both failed with "No response from API"; recurring failures of this kind on several worker VMs have no established cause, and no other model, account or paid tier was substituted. The lead's source-route limitation for skill directories, whose Files ordinary page REST does not return, is resolved through the Notion Skills API: an operator read of both Core skills and a write canary on a disposable skill page; Core originals were then still unchanged. Workers have no Notion connection.

## Earlier native baseline

Use the tools actually exposed by the installed T3/provider versions. This guide
was written for **0.0.46-nightly.20261009.2861** (V2), with upstream source checked
on 2026-10-09; its earlier guidance and proof remain 2861 observations. The setup
baseline it was qualified on is **0.0.46-nightly.20261009.2873**: the model target,
option and runtime-mode guidance below comes from 2873 source and 2873 native
readbacks. At that time stable 0.0.45 did not supply this orchestration surface;
that is a historical observation, not a verdict on later stable releases. Source
inspection does not qualify an installation; record native proof separately.

Keep four states apart: dated native proof, functions released upstream, what
this installation actually runs, and what it enforces and has accepted. A released
function is not installed, and an installed one is not accepted until it works
here. The live roadmap of released and pending native functions is
[Agentic Systems #32](https://github.com/arcitai/agentic-systems/issues/32); stable-channel adoption
and its maintenance gates are [Agentic Systems #34](https://github.com/arcitai/agentic-systems/issues/34).
Wait for an official release instead of building a runtime, approval service,
monitor or bridge for a missing function.

## The operator thread

Use the owner's chosen persistent thread in the existing project. Its title may
be AgentOps or an owner-chosen name; neither its title nor its pin assigns the role or loads
skills. Read the project instructions and the selected Agent Ops skill/references
explicitly when taking ownership. Record whether those sources were discovered
natively or loaded by path. Reload them when context or harness changes. Other
threads in the same project retain their own assigned task; do not overwrite
shared AGENTS/CLAUDE instructions with the lead persona.

Keep a fixed operator thread pinned with native auto-settlement disabled for
that thread. Verify its environment and workspace, including after reconnect.
Read current work, authority and priority before starting a task. Setup belongs
to Foundation; no extra lead project or task database is needed solely to keep
this thread visible. A connection's label or device icon is not execution proof:
verify the selected host/account and bound checkout with a harmless native turn.

## Execution and recovery

Start with `orchestrator_capabilities` to discover the actual available providers,
models and permission limits. When a writer needs its own workspace, use the
qualified worktree-bound launch below and verify the binding before it writes.
Use `delegate_task` for bounded work that can safely use its actual inherited
workspace, such as a read-only review; a worktree request in its prompt is not a
binding. Supply requirements, authority, workspace and evidence pointers:
the child does not receive the parent's full context. For `delegate_task`, use a stable
`clientRequestId` for retries of that task within the same provider session and
retain its task and child-thread IDs. After a new session, inspect durable work
before retrying; the old retry key does not deduplicate across sessions.
Read the terminal result through the returned result or `task_status`; a wait
timeout does not cancel the task. Progress or a cancelled run is not acceptance.

Take the target provider instance, model and option IDs/values from the live
capabilities, not from another product's model names. The worker contract inherits
options only when the child uses the same provider and model as the parent; set
the profile's options explicitly otherwise. Read back the child's actual selection
and modes with `t3_thread_configuration` before relying on them. A catalog entry
is not account authorization or a successful inference. Changing T3 new-thread or
project defaults is a settings change for Foundation, not part of delegation. If
the selected model is quota-limited or unavailable, report the native error and
reset; do not substitute another model, account or paid tier unannounced.

Choose each worker's runtime mode for its provider and task alongside the model,
and read back both. Each mode maps to a different provider policy: do not let a
Claude worker inherit the lead's Auto unexamined when the project qualified
Auto-accept edits for outside file edits. A pending approval or
question in a worker belongs to whoever holds that decision. Leave it visible,
answer only within existing authority, and never add an automatic self-approval
bridge. A superseded question can be dismissed through the native route without
inventing the owner's answer; a declined operation stays declined.

Decide before dispatch who prepares inputs, runs checks and owns generated
artifacts. When the lead is already authorized for that preparation, it may
validate an accepted archive's provenance, hash and safe regular members, confirm
the output is absent, and place the exact inputs and scratch in the worker's
verified task worktree through its own permitted route. Give the worker explicit
paths and the manifest. Prefer native Read/Edit for text work; the lead may keep
its authorized checks and artifact delivery. Sandbox and read/edit guards stay as
configured. Preparation is not a way to run a refused call as another actor, widen
roots or grants, or move an operation only to avoid a denial; new, unknown,
out-of-scope or denied actions stay held.

Detecting a waiting request is not authority to answer it. A T3 desktop/Connect
input or approval alert opens the thread; it does not wake an agent or grant a
decision. A native scheduled webhook is inbound and does not emit approval events.
The official [Claude](https://code.claude.com/docs/en/hooks) and
[Codex](https://learn.chatgpt.com/docs/hooks) hook references both document
`PermissionRequest` and direct MCP-tool hooks; Claude also documents `Notification`
with `permission_prompt` and HTTP hooks. These are candidate signals, not
installed or qualified here. The actual launch's setting sources, any SDK
override and the exact mapping to a T3 request still need qualification. The
closed [t3code #15082](https://github.com/pingdotgg/t3code/issues/15082) about
missing parent wait notifications is historical; the remaining upstream gaps are
linked from Agentic Systems #32. A notification, or the identity of a pending approval on a
delegated wait, never confers authority to decide another worker's approval. An
outside-agent MCP route with a writable mode spans the environment's projects; it
is not a per-project access list or an approval grant. Only a holder already authorized for that decision
may answer, after freshly checking the environment, project, thread, run, request,
full input and live callback. Never late-approve an aborted or resolved request.
Report one concrete handoff instead of polling or auto-confirming, then follow it
through.

Identify the actual authorized native responder and have the current request
settled with its real meaning. Deliver an already-accepted correction at a verified
supported checkpoint, then read the same bound worker's native activity for useful
progress. A handoff, resolved card, successful send or queued message is not
recovery. A blanket Decline can leave the run free to propose another call before
the correction arrives; it is not a recovery technique. Cancel may interrupt the
run and is not a neutral withdrawal: use it only when ending that blocked attempt
is authorized and its checkpoint is preserved, never on healthy work. Native state
can change during a handoff, so reconcile before each effect instead of declining
or replaying in a loop. A genuinely superseded question may be withdrawn only within existing authority through a supported native route; that is not an invented owner answer. A declined action remains declined. Refused actions stay refused; do not route them through
another actor or tool. If the current tools provide no capable responder, wake or
continuation, record that limitation and the next responsible holder in the
existing issue rather than building a custom layer.

A completed run need not end a worker's task: a harness background command,
monitor or child notification can start another turn in the same thread. Before
cleanup, restart, archiving or a completion claim, reconcile the worker's known
background tasks, resulting turns, pending requests/decisions and actual
workspace state; a first completed run alone is insufficient evidence. Find
background work in the worker's activity and later runs (`t3_thread_read`, or
`task_status` for a delegated child). Wait on the native notification or
terminal state, not an arbitrary sleep or poll loop.

Start each independent review round with a new `delegate_task` and a distinct
`clientRequestId`, producing a fresh reviewer context and task ID. Supply the
original brief, previous findings, responses and unresolved objections in its
prompt. Do not reopen a completed reviewer with `t3_thread_send` and call it a fresh review. Native
thread messages can coordinate authorized work, but cannot grant missing authority
or replace the owner's current decision. Inspect existing work after an uncertain
send before retrying; use the native retry key where the operation supports one.

Delegated children and `create_threads` may share the parent's checkout.
For writers requiring separate workspaces, use the supported explicit worktree-bound launch route,
or provision/select the worktree through the native UI before starting. Creating
a worktree in a prompt alone does not rebind the T3 thread. The inspected
`t3_thread_launch` route binds `workspaceStrategy` before starting the agent and
has no retry key. It cannot broaden the caller's runtime or interaction mode.
Do not widen permissions merely to expose a tool: use the established native route
or resolve the missing setup. After a lost launch response, inspect threads first.

When a running writer discovers upstream or instruction drift, stop before writes.
Reconcile terminal runs, background work and pending requests. Preserve the original
tracked, staged, unstaged, untracked and ignored task evidence, including file
bytes, modes and index; retain the original checkout and recovery material.
Obtain or confirm and retain the accepted reconciliation and target base within
existing authority before integration; drift does not authorize new scope.

For existing-worktree recovery, select an existing clean target checkout through
a supported native UI/operator route, guarded by the expected current worktree
binding. The pinned [Nightly 2873 UI branch selector](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/web/src/components/BranchToolbarBranchSelector.tsx#L433)
can select an existing worktree. The observed assisted recovery used the supported
client RPC [`thread.metadata.update`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/packages/contracts/src/orchestrationV2.ts#L2739)
with `expectedWorktreePath`; this was an operator-assisted client operation, not
an exposed MCP operation. Exposed [`t3_worktree_handoff`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/server/src/mcp/WorktreeMcpService.ts#L145)
rejects an already attached worktree and cannot move a thread between existing
worktrees. `t3_thread_launch` binds a new ordinary top-level writer; it does not
recover the same thread.

Make the first resumed turn read-only: reread the actual native binding, cwd,
Git root, branch and HEAD against the accepted target, then read its new canonical
instructions and needed skills before any integration. Compare the actual strong
provider-native thread identity and provider record/session before and after the
move. The same T3 conversation ID alone is insufficient: provider resume can
[fall back to a fresh context](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/server/src/orchestration-v2/ProviderTurnStartService.ts#L672).
If native identity changes or cannot be established, report a fresh/handoff
context rather than same-worker continuity. If the accepted task requires
same-worker continuity, stop integration and return the explicit handoff/replacement
decision; labeling a context fresh does not authorize a replacement. Honor existing
scoped owner authorization for handoffs or replacements where it applies.

After reconciliation and readback, integrate only the accepted task intent,
keeping current upstream-owned fields, instructions and unrelated files intact.
Verify that the original files, modes and index still match the retained evidence;
never silently replay a stale patch or discard evidence. If the supported route
or required evidence is unavailable, leave recovery pending with the concrete
operator gap. Do not add a bridge, runtime, self-approval or duplicate writer.
The 2026-10-11 observation demonstrated assisted same-worker recovery in one local
synthetic fixture; it does not qualify universal autonomous recovery or delivery.

Provider handoff carries bounded history and omits native tool state and
attachments. Give the receiving agent explicit task/candidate/evidence pointers;
do not promise transparent shared memory or cross-host execution.

The first turn after V1 migration also starts a fresh provider session. Read the
recent transcript, reload the project instructions and selected skills, and
recover outstanding authority and evidence before continuing. Imported messages,
pins and titles do not prove that a live provider session or its old tool state
survived. Keep the original database and the installation's recovery copy.

A persistent host service and the connection's lifecycle must be qualified
together. An SSH-managed server can have a different shutdown behavior from an
independently running service. Inspect before restarting, updating or moving work.
Unknown work remains unknown until native history or source state resolves it.

Use the lead's native chat as the decision channel. Mobile notifications use T3's
app/Connect route; they are not ChatGPT/Codex chat messages. Check delivery and
current candidate before accepting a response. External messaging is optional
and needs its own selected recipient, credential and reply policy.

For approved backlog operation, first prove one assignment end to end. Use an
available native schedule/webhook only when selected, with bounded scope, trusted
sender/admission rules and tested duplicate/offline behavior. A GitHub issue event
is input for the lead, not authority to execute arbitrary issue text.
