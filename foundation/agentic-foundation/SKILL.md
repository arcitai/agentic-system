# Agentic System Foundation

Use for requested setup, adoption, migration, maintenance or a readiness assessment. Whichever agent is asked applies it: the project's own agent, the owner's assistant or a helper. It is a method, not a standing Foundation agent, and ordinary work does not have to pass through it. Assessment is read-only. Preserve the project's purpose, existing tools, instructions, artifacts and useful work. Setup does not admit new product work.

Prepare for how the work runs. One project agent carries an accepted task from research to a checked result on the model the owner selected, and calls a fresh reviewer, a pair or parallel helpers when that adds something. Do not prepare a manager, a chain of stage agents or a model per stage by default. An installation that already runs another arrangement keeps it, with its grants and holds, until its own decision changes it.

Identify the owner, intended outcome, project records, execution environment, where the owner reaches the work, and the delivery destination. Recover facts from the actual sources before asking the owner to repeat them. Use the existing project record; do not create a second tracker. Resolve the project definition from its owning source: the original in the chosen context home is the editable one, and a version-marked export records one revision. It states intended choices. Verify applied native configuration separately and preserve existing authority and holds.

## Foundation scopes

**Agent environment:** selected client/host, native agent tools, the owner-selected model, selected skills, identities/connections, effective permissions, native history, startup and recovery. The bundled host references use T3 Code as a worked example, not a required server. Another native tool is suitable once its needed loading, execution and access behavior is checked.

**Project foundation:** authoritative context, goal and mandate, selected methods, native artifacts, meaningful acceptance checks and applicable standards. Software may use a repository; BI may use models and workspaces; research may use documents and datasets. Keep their native sources.

**Operations & maintenance:** the work/test/delivery/operating environments the task needs, observable failures, updater ownership, maintenance windows, recovery and relevant ongoing care. The agent host and the delivered product may run on different systems. A prototype does not require every production control.

These are preparation scopes, not three machines, agents or access levels. Prepare only the capabilities the intended work requires. Reuse unchanged proof; recheck the affected capability after a relevant version, account, permission, configuration or dependency change.

## Adopt or update an existing project

Use [the adoption guidance](references/adoption.md#update-an-existing-project) when an existing project should align with a selected reviewed revision. Compare installed methods and local adaptations before changing files; preserve product work, context and current authority. A project visible in a workspace is not necessarily an adopted installation.

## Context, methods and skills

Resolve each artifact's original source. Shared method, policies and authored skills live in the chosen context home; project-native artifacts and technical work records stay in their native systems. The context home is replaceable. Until an explicit cutover, an existing source keeps its authority for its version.

For a project without its own setup yet, select or create its context home, reuse its existing sources, and prepare only the definition, methods and access the intended work needs. Its product goals, architecture and delivery belong there. The public guide supplies methods to select or link, not a document tree to clone.

A project's work module is the methods, checks and domain knowledge it selects for its kind of work. Native harness behavior, the project's own instructions, an optional method package or a domain method can each be sufficient; none is required, and no package is a dependency. Record the selection as links with versions. It is not a plugin, manifest or directory.

Keep project bootstrap instructions thin: common constraints, source routes and checks, and what an agent could not infer from the project. A role title, thread name or `AGENTS.md` does not load a skill or grant access. Keep required references inside each selected skill bundle and identify source and version when adopting a reviewed distribution or giving a helper its files. Do not invent a sync service or silently refresh installed skills.

## Prove the boundaries and operation

- Read the actual versions, selected provider/account, tools and effective native settings. A binary, connection, copied skill or available model name is not a working installation.
- Describe access by environment and grant, not by role title: the owner's personal access, the project agent's project-scoped environment, and any narrower environment a helper runs in. Changing how work is organised neither widens nor removes a grant, and existing isolated helper environments stay until separately changed. Processes sharing an execution identity may share its files, connections and brokered reach; verify the actual native controls. A fresh context or a worktree separates thinking and changes, not readable files or credentials. A helper or reviewer that must not have the project agent's reach needs its own enforced boundary and receives selected files, not the connection.
- For each source or project-service connection, agree its targets and operations, credential's OS account, storage and delivery, expiry, revocation route and responsible holder. Check actual allowed and refused access. For GitHub, use the scoped connection guidance in [references/github.md](references/github.md); a personal login or role name is not proof of the agreed boundary.
- Where an agent must use a credential without receiving its value, use a native credential broker outside its execution boundary. A secret store or redacted field does not establish this; readable mounts and environment variables deliver the value. Bind credentials to the selected project and environment through native controls, keep only references in context and definitions, and verify useful service access, an out-of-scope refusal, unreadable raw values, wrong-environment refusal and withdrawal of access, including cached credentials and global fallback.
- Scope a context-home connection to the selected project pages and only the operations its work is authorised for; keep the owner's personal context outside it. Read-only access cannot write progress: use the native task record or a scoped handoff until an authoring route is authorised. If an inherited connector exceeds the accepted access, hold the dependent execution until the exposure is removed, isolated or resolved by the owner. An instruction is not the repair.
- Check an allowed operation and one that should be refused in the environment that will actually run the work. Record success, approval request, permission denial and OS refusal distinctly. A document's claim is not proof of enforcement.
- Make sure the work can be visibly wrong, in proportion to what depends on it: actual project checks and relevant failure paths. Distinguish source inspection, a rehearsal, installed behavior and the delivered outcome. If no suitable domain method exists, agree task-specific checks and disclose the gap.
- Record the owner's model selection, and any explicit delegation of that choice, where the project keeps persistent choices, and read the native selection back. A setup includes no silent fallback, paid overage or account switch.
- Agree update ownership for a shared host; this remains an owner choice, and until it is set update decisions go to the owner. An idle maintenance window has no active or unknown writers on the affected host. Reconcile them before changing versions, stopping services or rebooting. Keep a recoverable starting state, verify affected operation afterwards and preserve private native history.
- Qualify the recovery behavior the intended unattended work depends on, using disposable tasks. Unqualified restart or update behavior holds actions that depend on it; other authorised work continues where interruption is harmless and the limitation is disclosed. Updates, approval prompts, machine login and encrypted-disk unlock may need different recovery routes. Native scheduling is optional and needs an authorised, tested configuration.
- Keep credentials in native secret stores and sensitive host/account details in private installation records. A private record of a permission does not apply it or enforce its expiry.

Preserve explicit admission/delivery delegation and stop conditions. A new grant must identify the needed operation, target, authoriser and removal condition. No role title, skill or thread name grants administration or delivery authority.

## Hand over a readiness result

For each required capability, record its scope, owning source, disposition and retained evidence:

- **Verified:** an actual check/readback or applicable dated proof supports the claim.
- **Required gap:** unchecked, inaccessible, conflicting or failed prerequisites remain visible, with the next action and responsible holder.
- **Conditional / not needed:** explain why the intended work does not depend on it.

A required gap holds dependent work, not unrelated authorised work. A recorded gap is not readiness. Give the result to the owner and the project's existing record, where the project agent finds it. A setup gap found later during work reopens that capability only, not the whole setup.

## Bundled references

Read [references/policy.md](references/policy.md) when taking on work in a project under this method, or when a question of authority, model choice, helpers and review, source ownership, restart or evidence comes up. A project's bootstrap instructions can route to it. It states facts and limits, not a workflow.

An assistant outside the project can use the optional `agentic-entry` skill to explain the method, find the right project and start, continue or check work there; install it by the native route in [references/setup.md](references/setup.md). Without it the owner addresses the project agent directly. To compare alternatives when a decision depends on it, use `agentic-evaluate` where available. For a personal method package changing identity, consult [references/method-migration.md](references/method-migration.md); Agentic System depends on no such package.

For software/T3-specific preparation, consult only the relevant bundled reference: [references/adoption.md](references/adoption.md), [context.md](references/context.md), [engineering.md](references/engineering.md), [ci-delivery.md](references/ci-delivery.md), [github.md](references/github.md), [setup.md](references/setup.md) or [workspace.md](references/workspace.md). These references retain their observed versions/dates; old worked examples are not current installation proof. Qualify them against the chosen tools before applying them.

Agentic System Foundation installs no daemon and grants no authority beyond the request.
